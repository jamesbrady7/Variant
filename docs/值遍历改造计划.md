# 值遍历（ValueSink）改造计划

> 状态：**已实施**（2026-11-01）。分支 `feature/container-traits`。
> 前置提交：`ff95337`（容器 traits + 自动归一化）、`c366d39`（Python 桥接入归一化、删逐类型 hook）。
> 实施提交：`3528a00`（core：ValueSink/visitValue/VariantSink）、`4e2fd6e`（binding：PySink + demo 断言）。
> 实施中的调整见文末「实施记录」，与本节设计不一致处以记录为准。

## 1. 问题

扩展槽里的标准容器，目前统一走 `normalizeToVariant` 变成 Variant 正规形，
再交给各边界转换。但两条边界的需求不同：

| 边界 | 键的要求 | 原因 |
| --- | --- | --- |
| JSON / 二进制 | 只能是字符串 | RFC 8259：JSON 成员名必须是字符串 |
| Python | `dict` 键可以是任意 hashable，int 就该是 int | Python 对象模型 |

共用一种中间表示 ⇒ `map<int,int>` 在 Python 里只能拿到 `{"1": 2}`。
这不是"匹配错了容器"，而是 Variant 的 Map 表示只有字符串键；归一化时的
`Key = int` 是编译期已知的，只是没有地方放。

## 2. 决策

- **JSON / 二进制保持 Variant 正规形不变**（键字符串；二进制靠 `$type` 在解码时
  按 `key_type` 解析回 int）。已有数据和测试不动。
- **Python 改为按编译期类型直接产出 `PyObject*`**，不经过 Variant 表示，键保留真实类型。
- 两者共用**同一份编译期递归**，通过 Sink 分流。
- 明确的不对称（写进手册）：**Python → C++ 仍字符串化**——Python dict 的键类型
  在进入 Variant 时没有落脚点（VariantMap 只有字符串键），`getAs<map<int,...>>` 负责解析回来。
  只有"C++ 知道类型"的那一侧才保留键类型。

## 3. 设计

```
             visitValue<T>(value, ValueSink&)        ← 编译期递归，只有一份
                /                        \
        VariantSink                      PySink（binding 实现）
     → Variant 正规形                 → PyObject*
     → JSON / 二进制 / codec          → dict/list，int 键仍是 int
```

### 3.1 接口（`vt/normalize.h`，不依赖 Python）

```cpp
enum class MapKeyForm { Text, Typed };   // Text = 键可无损写成文本（VariantSink 用 Map）
                                          // Typed = 键只能原样给（VariantSink 用 [[k,v],...]）

struct ValueSink {
    virtual ~ValueSink() = default;
    virtual void onNull() = 0;
    virtual void onBool(bool) = 0;
    virtual void onInt(std::int64_t) = 0;
    virtual void onDouble(double) = 0;
    virtual void onString(std::string_view) = 0;
    virtual void onVariant(const Variant&) = 0;      // 已成型的 Variant，不拆解
    virtual void onExtension(const std::any&) = 0;   // 叶子自定义类型
    virtual void onListBegin(std::size_t) = 0;
    virtual void onListEnd() = 0;
    virtual MapKeyForm onMapBegin(std::size_t size, bool keyConvertible) = 0;
    virtual void onMapEnd() = 0;
    virtual void onEntryBegin() = 0;
    virtual void onEntryEnd() = 0;
};
```

- `keyConvertible` 在编译期由 `map_key_traits<Key>::convertible` 决定；
  sink **返回**它要的键形态（"能不能"归编译期，"愿不愿意"归边界），
  visitor 校验：不可转换的键一律按 `Typed` 走。
- `PySink` 永远返回 `Typed`，键按事件原样构造。

### 3.2 遍历器

`visitValue<T>` 的规则与现在的 `normalizeToVariant` 完全一致：

- `Variant` → 原样交给 sink（`onVariant`，不拆解，保证序列化行为不变）；
- Sequence / Map / Pair → 递归；
- 标量 / string / string_view / char* / nullptr → 对应 `on*`；
- 其它叶子 → `onExtension(std::any(value))`。

`normalizeToVariant` 保留为 `VariantSink` 的一行包装，**序列化路径零改动**。
`getAs` / `denormalizeFromVariant` 不动（那是反向）。

### 3.3 注册表

`NormalizerRegistry` 的签名从 `Variant(*)(const std::any&)` 改成
`void (*)(const std::any&, ValueSink&)`（`installContainerAdapters<T>` 里
`visitValue<T>` 的包装）。
登记点仍在 `Variant::fromValue<T>`（`installContainerAdapters<T>()`），
`vt::registerContainerAdapters<T>()` 仍是只读进程的编译期锚点。

### 3.4 PySink（`binding/core/variant_python.cpp`）

- 栈帧：正在构建的 list / dict；dict 帧里 `key` 非空表示"下一个到达的是值"；
- 叶子 `onExtension(any)` → 走现有 vpy Hook 表（对象/值/共享），不再"先变 Variant"；
- **键不可哈希时响亮失败**：`PyObject_Hash(key) == -1` 就 `PyErr` + 失败，
  不能悄悄退回字符串键（指针键 map 用 shiboken wrapper 做键时就可能是不可哈希的）。

## 5. 已否决的方案（记录原因，避免重走）

| 方案 | 否决原因 |
| --- | --- |
| 给 Variant 加 `IntMap` 槽（P3） | 改数据模型（Type 枚举/相等/describe/路径/二进制 tag），且键类型是开放集合，会滑向"每种键一个槽" |
| 非字符串键统一写 `[[k,v],...]`（P1） | JSON 也变成嵌套数组，与已有 `{"1":2}` 数据不兼容 |
| 形状描述符（P2） | 先字符串化再由桥还原，多的是一次"编码再解码"，且只修 C++→Python 一半；Sink 方案同样只修这一半但不需要还原 |
| 逐类型手写 Python hook（旧 `container_hooks.*`） | 不递归、要序列化另写一份，已删除 |

## 6. 风险

- shiboken wrapper 的 `__hash__`：指针键 map 在 Python 侧可能不可哈希 → PySink 必须报错；
- PySink 与共享所有权 hook 的交互（借用的对象、capsule）要与现有 `toPython` 行为一致；
- JSON/二进制输出**必须逐字节不变**，这是本次改造的回归门槛。

## 7. 实施记录（与上面设计的差异）

1. `onMapBegin` 的签名改为 `MapKeyForm onMapBegin(std::size_t size, bool keyConvertible)`
   ——由 **sink 选择**要哪种键形态，visitor 校验（不可转换的键强制 `Typed`）。
   原设计是 visitor 编译期决定后传进 sink，但那样 PySink 拿不到真实键；
   现在"能不能"仍是编译期（`keyConvertible`），"愿不愿意"归边界。
2. 多了一个事件 `onVariant(const Variant&)`：`visitValue<Variant>` 不拆解，交给 sink。
   `VariantSink` 原样保留（与改造前 `normalizeToVariant(Variant)` 完全一致，避免
   重建 map 改变顺序）；`PySink` 直接调用既有 `toPython`。
3. `canConvertToPython` 没复用 PySink，而是单独的 `ConvertCheckSink`：预检不应该
   构造 Python 对象，也不应该触发 hook 的副作用。键的可哈希性无法在预检阶段判断，
   留到实际转换时由 Python 判（失败即 TypeError）。
4. 不可哈希键的测试用 `map<vector<int>, int>`（键在 Python 是 list），
   没有依赖 shiboken wrapper 的 `__hash__` 行为；对象键的正例用
   `map<DemoNode*, string>`（`makeNodeKeySample`），实测 shiboken 对象可哈希。
5. 回归水位：`vt_tests` 211 → 222（`testValueSink` 用自定义 `TraceSink` 锁定
   "Text/Typed 由边界选、不可字符串化的键强制 Typed"；`testNestedContainers`
   补 `vector<bool>` 代理回归）、`vt_serial_tests` 1821、`vt_shared_tests` 33、
   `vt_plugin_override_test` 31 不变；`py_scripts/demo.py` 42 → 50 项。
