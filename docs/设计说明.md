# vt::Variant 设计说明

> 目标：一套接口友好、性能可量化的、不依赖 QVariant 的类型擦除容器；
> 支持路径式访问、运行时类型注册，并能通过 shiboken 与 Python 原生对象双向转换。

---

## 1. 总体结构

```
┌─────────────────────────────────────────────────────────────┐
│ Python / numpy / 业务脚本                                    │
│   dict / list / int / float / str / None / 注册的绑定对象      │
└───────────────────────┬─────────────────────────────────────┘
                        │ shiboken 包装 + 转换
┌───────────────────────▼─────────────────────────────────────┐
│ variant_binding.pyd                                          │
│   PyDocument（只含安全签名） + pyDocGet/pyDocSet/pyEcho/...   │
│   variant_python_bridge（静态库）：                           │
│     vpy::toPython / vpy::fromPython（递归）                   │
│     vpy::registerPointerType / registerValueType /          │
│          registerSharedType（注册表）                       │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│ variant_core.dll（纯 C++17，零 Qt / 零 Python）               │
│   Variant / VariantMap / VariantList / Path                   │
│   VariantDocument / TypeRegistry / describe()                 │
└─────────────────────────────────────────────────────────────┘
```

分层原则：**核心不认识 Python，Python 层不认识 QVariant**。Qt 只出现在 benchmark 里。

## 2. Variant 的存储

```cpp
using Storage = std::variant<
    NullTag,                          // null
    bool,
    std::int64_t,
    double,
    std::string,
    std::shared_ptr<VariantMap>,      // 递归类型必须间接持有
    std::shared_ptr<VariantList>,
    std::shared_ptr<VariantExt>       // 内部是 std::any
>;
```

### 2.1 为什么是 variant + any，而不是纯任何一个

- `std::variant` 是**编译期封闭集合**，运行时注册新类型在语言层面不可能；
- 纯 `std::any` 可以注册，但标量也会走 any 的存储/分派；
- 因此取两者并集：**前 7 槽是零分配快路径，第 8 槽 any 是扩展出口**。

### 2.2 any 为什么要再套一层 shared_ptr

MSVC 的 `std::any` 本身是 **64 字节**。直接把它作为 variant alternative，
`sizeof(vt::Variant)` 会变成 **72**。改成 `shared_ptr<VariantExt>`（内部才放 any）
后，布局由 `std::string`(32) 决定：

```
sizeof(vt::Variant) = 40    （QVariant = 16）
```

也就是说：标量和字符串仍然内联；只有扩展类型多一次堆分配——而扩展类型通常
本来就是指针（对象类型），这次分配可以接受。

### 2.3 COW（写时复制）

`VariantMap` / `VariantList` 由 `shared_ptr` 持有：

- 拷贝 Variant = 拷贝 shared_ptr，O(1)；
- 通过非 const 入口（`asMap()` / `asList()` / `operator[]`）访问时，
  若 `use_count() > 1` 就克隆整棵容器（detach）；
- **只读必须走 const 引用**：

```cpp
Variant copy = original;
copy["k"] = 2;               // 触发 detach，original 不变

const Variant& ro = copy;
ro.asMap().size();           // 不 detach
copy.asMap().size();         // ⚠ 非 const，可能 detach（若仍共享）
```

这条不是理论风险：benchmark 初版在 500 万次只读里用了非 const 的
`asMap().size()`，每次都克隆 10k 条 map，直接跑了 2 分钟。

### 2.4 值语义边界

- 标量、字符串：深拷贝（`std::string` 带 SSO）；
- map/list：COW；
- 扩展对象：`std::any` 的值语义（对象类型的指针本身被拷贝，指向同一对象）。

`operator==` 对扩展类型只比较动态类型（`std::any` 没有通用相等语义）。

## 3. 路径系统

### 3.1 语法

| 写法 | 含义 |
| --- | --- |
| `a.b.c` | 连续键 |
| `a[0].b` | 键 + 下标 |
| `a[0][1]` | 连续下标 |
| `["a.b"]` | 带引号的键（键里含点号/方括号） |
| `["a\"b"]` | 引号内支持 `\"`、`\\` 转义 |
| `""` | 空路径 = 根自身 |

### 3.2 类型区分：字符串是键，Path 是路径

```cpp
using namespace vt::literals;

v["a.b"];          // 字面键 "a.b"
v["a.b"_path];     // 路径 a -> b
v[0];              // list 下标

v.find("a.b");            // 键：缺失返回 nullptr
v.find("a.b"_path);       // 路径：缺失返回 nullptr
v.at("a.b");              // 键：缺失抛 KeyNotFound
v.at("a.b"_path);         // 路径：缺失抛 KeyNotFound/NotAMap/...
v["a.b"_path] = 1;        // 路径写入：自动建中间节点
bool ok = v.set("a.b"_path, value);   // 不抛，失败返回 false
```

`Variant` / `VariantMap` / `VariantList` 三个根使用**同一套方法名**，
只靠参数类型区分键与路径。早期的 `literal()/findLiteral()/containsLiteral()`
等第二套名字已删除。

### 3.2.1 为什么 `operator[]` 只保留 `string_view` 入口（C++ 实测坑）

如果同时提供 `operator[](std::size_t)` 与 `operator[](const char*)`，
那么 `v[0]` 会二义：字面量 `0` 既是整型，也是空指针常量
（MSVC 报 C2593）。因此 `operator[]` 只保留：

- `operator[](std::string_view)`（键；字面量/`std::string` 自动转换）
- `operator[](std::size_t)`（下标）
- `operator[](const Path&)`（路径）

`find/at/contains/getAt` 没有数字重载冲突，可以保留 `const std::string&` 热路径重载；
但 `operator[]` 不行。这是一条用编译器换来的约束，不要随意加回 `const char*`。

### 3.3 创建规则

- 键段遇到 Null：自动创建 map；
- 下标段遇到 Null：自动创建 list；
- 下标只能 `index <= size`：等于 size 追加一个 Null，大于 size 抛
  `IndexOutOfBounds`（不允许凭空跳号）；
- 穿过的节点不是 map/list：抛 `NotAMap` / `NotAList`。

### 3.4 预编译路径

```cpp
const vt::Path p = vt::Path::parse("a.b.c.d.e");
v.at(p);                          // 39 ns/次
v.getAt<int64_t>("a.b.c.d.e"_path);  // 281 ns/次（每次重新解析 + 字符串分配）
```

`_path` 是运行时解析；如果要复用到热循环，提前构造 `Path`。

热循环里必须预编译。这是"友好语法"的税，换来的是可读性。

### 3.5 错误对象

```cpp
enum class VariantErrorCode {
    SyntaxError, EmptyPath, NotAMap, NotAList,
    KeyNotFound, IndexOutOfBounds, TypeMismatch, OutOfRange
};
```

`OutOfRange` 不只服务路径：整型构造里无符号值超过 `INT64_MAX` 也抛它，
避免 `static_cast<int64_t>` 静默回绕成负数。

`VariantError` 除了 message 还带 `code()`、原始 `path()`、第几段 `segment()`、
该段在路径串里的 `offset()`。错误信息示例：

```
[NotAMap] segment 2: expected map, got int (path="cfg.nested.deep", segment=2, offset=11)
```

## 4. 类型注册

### 4.1 C++ 存储层是开放的

`Variant::fromValue(T)` 就是 `std::any`，**不需要任何注册**：

```cpp
struct Probe { int id; };
Variant v = Variant::fromValue(Probe{7});
v.get<Probe>();                 // optional<Probe>
```

注册不是存储门槛，而是**边界**需要的元数据。存在两张表：

| 表 | 位置 | 用途 |
| --- | --- | --- |
| `vt::TypeRegistry` | core | 稳定名字（describe / 日志 / 将来的序列化） |
| `vpy` Hook 表 | binding | 类型 ↔ Python 转换器 |

`vpy::registerPointerType<T>` / `registerValueType<T>` **一次调用同时写两张表**：

```cpp
vpy::registerPointerType<DemoNode>("variant_binding", "DemoNode");
// 等价于：
//   TypeRegistry::registerType<DemoNode*>("DemoNode");
//   Python Hook 表加入 (typeid(DemoNode*), DemoNode 转换器)
```

名字冲突（同一名字已被另一种 C++ 类型占用）会返回 `false`，不会注册 Hook。

### 4.2 边界预检

在把数据交给 Python 之前，可以先问"这棵树能不能整体转换"：

```cpp
bool vpy::canConvertToPython(const Variant& value);   // 递归检查 map/list/扩展槽
```

任一层出现没有 Hook 的扩展类型就返回 `false`，而不是在深层元素上抛异常。
Python 侧对应的函数是 `variant_binding.canConvertToPython(value)`。

未注册类型跨 Python 时仍然会**响亮失败**（`TypeError` 带类型名），不会静默丢值。

## 5. shiboken 绑定：为什么全是 PyObject 直通

最初的设计是教科书式的：把 `vt::Variant` 声明为 `primitive-type`，写一份
conversion-rule，让所有真实签名的函数自动转换。实际踩到三个硬问题后改成
**PyObject 直通 + C++ 手工递归转换**。

### 5.1 坑一：typesystem 不再接受 `ns::Class`

```xml
<object-type name="vt::VariantDocument"/>
```

```
error GD60709C2: Nesting types by specifying '::' is no longer supported
```

shiboken 6.10.3 只接受不带命名空间的类型名。可绑定类必须放在全局命名空间
（本项目把 `VariantDocument` 移到了全局；`DemoNode` / `DemoColor` 同理）。

### 5.2 坑二：Python 签名解析器不认识 `vt.Variant`（会 fatal）

把 `vt::Variant` 声明成 primitive-type 后，正常调用是通的，但一旦参数类型
不匹配，shiboken 的错误处理要解析签名里的 `vt.Variant`：

```
UNRECOGNIZED: 'vt.Variant'
OFFENDING LINE: 'variant_binding.echo(arg__1:vt.Variant)'
...
AttributeError: 'str' object has no attribute '__module__'
Fatal Python error: libshiboken: seterror_argument did not receive a result
```

即：**错误路径会把进程打死**。这不是可接受的库行为。

### 5.3 坑三：自动绑定不支持 `PyObject*` 形参/返回值

把 `PyDocument::get` 写成返回 `PyObject*`、`set(..., PyObject*)` 后，
自动生成的 wrapper 里出现：

```
error C2661: Shiboken::Conversions::copyToPython: 没有重载函数接受 0 个参数
error C2065: "cppArg1": 未声明的标识符
```

正确姿势是：类只保留 shiboken 能自动处理的签名（`bool` / `std::string`），
跨语言值用 **add-function + inject-code**，参数写 `PyObject`，函数体里手工转换。

### 5.4 最终形态

```xml
<object-type name="PyDocument"/>

<add-function signature="pyDocGet(const PyDocument*, const std::string&amp;)">
    <inject-code class="target" position="beginning">
        return pyDocGet(cppArg0, cppArg1);   <!-- 直接返回 PyObject* -->
    </inject-code>
</add-function>

<add-function signature="pyDocSet(PyDocument*, const std::string&amp;, PyObject)">
    <inject-code class="target" position="beginning">
        bool ok = pyDocSet(cppArg0, cppArg1, %PYARG_3);  <!-- 第 3 个原始参数 -->
        ...
    </inject-code>
</add-function>
```

注意 `%PYARG_3`：混合签名里的 `PyObject` 参数不会生成 `cppArgN`，必须用
`%PYARG_n` 取原始 Python 对象。

### 5.5 Py_LIMITED_API

shiboken 在部分配置下传播 `Py_LIMITED_API`，届时 `PyTypeObject` 字段不可见、
`PyList_SET_ITEM` / `PyUnicode_AsUTF8AndSize` 等宏缺失。本项目在
`variant_python.h` / `py_document.h` 的**最顶部**：

```cpp
#if defined(Py_LIMITED_API)
#undef Py_LIMITED_API
#endif
#include <Python.h>
```

我们链接的是完整 `python39.dll`，所以这样做是安全的。

### 5.6 Debug 配置的限制

Windows 官方 Python 不带 `python39_d.lib`。Debug 下 `_DEBUG` 会让 `pyconfig.h`
定义 `Py_DEBUG`，引用 release 库里不存在的：
`_Py_RefTotal`、`_Py_NegativeRefcount`。

因此 **binding / exe 只在 Release 构建**。core / tests / bench 双配置均可。

### 5.7 Python 侧映射

| C++ Variant | Python |
| --- | --- |
| Null | `None` |
| bool | `bool`（必须先于 int 判断） |
| int64 | `int`（溢出报 OverflowError） |
| double | `float` |
| string | `str`（UTF-8） |
| map | `dict`（键必须是 str） |
| list | `list`（也接受 tuple，转成 list） |
| 注册的对象类型 | 同一个 Python wrapper（`is` 保持） |
| 注册的值类型 | 拷贝出来的 Python 值对象 |
| 注册的共享类型 | 同一个 Python wrapper（`is` 保持），生命周期由 capsule / 收养共用 |

### 5.8 新增一个可跨语言的类型

1. 在业务头里声明类并加入 shiboken 的 `HEADERS` 与 typesystem
   （对象类型 `<object-type>`，值类型 `<value-type>`，**全局命名空间**）；
2. 在 `demo_registration.cpp` 里加一行（这一行同时登记核心名字和 Python 转换器）：
   ```cpp
   registerPointerType<MyNode>("variant_binding", "MyNode");   // 对象类型存 T*
   registerValueType<MyColor>("variant_binding", "MyColor");   // 值类型存 T
   registerSharedType<MyShared>("variant_binding", "MyShared"); // 共享类型存 shared_ptr<T>
   ```
3. 重新构建。转换规则不需要改。

### 5.9 共享所有权：为什么用 capsule，而不是 shiboken 智能指针

需求：C++ 侧以 `std::shared_ptr<T>` 持有一批对象，Python 也要按普通 `T` 使用它们，
两边谁先死都不能让对象提前析构。

**否决过的方案**：shiboken 的 `smart-pointer-type`。本机 shiboken6 实测可用，但
Python 看到的是 `SharedNodePtr` 包装物（`isinstance(node, SharedNode)` 失败）；
生产环境用的 shiboken2 文档更明确：该特性只支持 `type="shared"` 且仅限函数返回值。
依赖它会让“Python 侧就是 T”这条承诺落到绑定器版本上。

**最终方案**：C++ 侧存 `shared_ptr<T>`，`toPython` 时返回真正的 `T` wrapper，
再把一份 `shared_ptr<T>` 的拷贝放进 wrapper 上的 **PyCapsule**（属性
`_vt_shared_owner`，capsule 名 `vt::shared_owner`）。capsule 的析构函数负责释放
这份拷贝。Python 侧看不到任何句柄类型。

两个方向的转换规则：

```
C++ shared_ptr<T> ──► wrapper(T) + capsule(shared_ptr 拷贝)
Python wrapper   ──► 有 capsule ?  拷贝 capsule 里的 shared_ptr
                     无 capsule 且 owning ?  收养（shared_ptr 用 keep-alive deleter）
                     无 capsule 且 borrowed ? TypeError
```

**收养（adoption）**：Python 创建、由 Python 独占的对象第一次写入 Variant 时，
没有现成控制块可用。做法是构造 `shared_ptr<T>(raw, PythonKeepAliveDeleter)`：
deleter 不 delete `T`，而是持有一份 wrapper 的强引用 —— 只要 shared_ptr 还活着，
wrapper 就不会被 GC，Python 也就不会 delete `T`；最后一个 shared_ptr 释放时
DECREF wrapper，真正的析构仍由 Python 完成。这样两种所有权模型可以共存，
且不需要转移所有权。收养结果按 `raw -> weak_ptr` 登记，同一对象只建一个控制块。

拒绝借用对象（`hasOwnership == false` 且无 capsule）是刻意的：收养它会导致
C++ 与 Python 双重 delete，假装共享则会在 C++ 所有者析构后悬空。
没有安全的降级路径，所以边界直接 `TypeError`。

避坑两条（实现层面的硬约束）：

1. **已经收养的对象不能再挂 capsule**：deleter 持有 wrapper、wrapper 持有 capsule，
   capsule 又持有 shared_ptr，引用环会让对象永不释放。
2. **deleter 里碰 Python 必须先 `Py_IsInitialized` 再 `PyGILState_Ensure`**：
   退出期 shared_ptr 可能在解释器 finalize 之后才释放。

代价与已知限制：收养表按 `T*` 索引，依赖“指针在对象存活期间唯一”这一常规分配器行为；
表里存 `weak_ptr`，对象析构后条目失效，下次查到时先清理——地址复用不会误认旧对象。
序列化按值编码，不保留共享关系。

## 6. 性能实测（Release / MSVC 2019 / 本机）

10k 键 map；`qt/vt > 1` 表示 vt 更快。

| 场景 | vt | QVariant | 倍率 |
| --- | ---: | ---: | ---: |
| copy int64 + 读取 | 5.2 ns | 11.1 ns | 2.1x |
| copy double + 读取 | 5.0 ns | 4.3 ns | 0.87x |
| copy 8 字符 string + 读取 | 9.5 ns | 30.7 ns | 3.2x |
| copy 128 字符 string + 读取 | 67.3 ns | 30.6 ns | 0.45x |
| 构建 10k 键 map | 1.10 ms | 2.27 ms | 2.1x |
| 10k 键 hash 查找 | 16.3 ns | 111 ns | 6.8x |
| 拷贝 10k 键 map（COW） | 14.7 ns | 31.3 ns | 2.1x |
| 5 层路径（预编译 Path） | 39 ns | 160 ns | 4.1x |
| 5 层路径（每次解析） | 289 ns | — | — |
| copy + 改一个键（1k map） | 72 µs | 49 µs | 0.68x |

解读：

- 结构性优势来自 `unordered_map`（Qt 是 QMap 红黑树）和预编译路径；
- 封装层本身没有额外开销：无虚函数、无 `std::function`、无堆控制块；
- 长字符串拷贝是唯一明显劣势：QString 隐式共享 O(1)，我们深拷贝；
- detach 两边都是 O(n)，Qt 的 QMap 节点复制略便宜；
- `sizeof` 40 vs 16：QVariant 更小，但大量依赖堆与隐式共享。

## 7. 已知限制

1. 绑定目标 Debug 不可用（见 5.6）。
2. 非 const 的 `asMap()` 会 detach；只读请用 const 引用（见 2.3）。
3. 路径字符串每次访问都要解析；热循环用 `vt::Path` 预编译（见 3.4）。
4. 扩展类型 `operator==` 只比较动态类型。
5. `VariantMap` 是 `unordered_map`，遍历顺序不稳定；需要顺序时用 list 或自行排序。
6. 跨线程访问同一个 Variant 无同步；Python 侧转换必须在 GIL 下。
7. `std::any` 持有值的析构函数在创建它的模块里，扩展类型需要保持对应 DLL 常驻。
8. 共享类型序列化按值编码，读回是新的 `shared_ptr`，不保留共享关系/对象身份（见 5.9）。
9. 借用对象（无 capsule 且非 owning）写入共享类型 Variant 会 `TypeError`，这是设计而非缺陷。

## 8. 序列化设计

目标：JSON（人类可读/跨系统）与二进制（体积/精确）共用一套类型语义，零第三方依赖。

> 逐条映射规则、往返矩阵、错误表和完整示例见
> [使用手册 第 6 章](使用手册.md)；本章只讲设计与取舍。

### 8.1 扩展类型：普通 Variant 作为中间表示

```
T  --codec.encode-->  Variant（只含内建类型）
   <--codec.decode--
```

好处：

- 每种类型只注册一次，JSON / 二进制自动都支持；
- 两种格式可以交叉验证；
- 核心库不认识业务类型。

注册表（`CodecRegistry`）与 Python 的 `vpy` Hook 表**互相独立**：
Python 关心 wrapper 身份，序列化关心值表示。

### 8.1.1 常见 std 容器的内建适配

| 类型 | 存储 | 理由 |
| --- | --- | --- |
| `vector<Variant>` / `map<string,Variant>` | 原生 List / Map | 与 Variant 容器同构，包扩展只会丢 dict 语义 |
| `vector<int>` / `vector<string>` / `map<string,string>` / `map<int,int>` | 扩展槽（紧凑） | 保留元素内存布局；`getAs<T>` 可从扩展槽或普通 List/Map 恢复 |

JSON 默认把内建容器写成普通数组/对象（codec 的 `plain` 标记），
`EnvelopeAll` 时才加 `$type`；二进制始终带类型名。
无类型的 `Variant` 无法从 JSON 数组/Python list 推断 `vector<int>`，所以读取端必须
显式 `getAs<T>` 或使用带类型的绑定入口——这是类型擦除的固有代价。

### 8.1.2 I/O 分层

核心只有字符串/字节缓冲 API；流和文件是薄封装：

- `writeTo(std::ostream&)` / `readFrom(std::istream&)`：先整段缓冲，再复用字符串实现；
- `writeFile(path)` / `readFile(path)`：二进制模式打开（避免 Windows 换行转换），
  **先序列化成功再打开文件**，因此编码失败不会留下半截文件；
- 路径 `std::string` 按 **UTF-8** 解释（`std::filesystem::u8path`）。MSVC 的窄字符
  fstream 默认按 ANSI 代码页打开，不做这一步中文文件名必然失败；
- 流/文件失败统一映射为 `SerializeErrorCode::IoError`，其余错误码保持不变；
- 文件接口与流接口都是**整段缓冲**，没有流式解析；大小受可用内存限制，
  GB 级数据需在应用层切分。二进制另有单值上限（`maxStringBytes` / `maxElements`，
  可在 `BinaryReadOptions` 调整），JSON 只有 `maxDepth`。

### 8.2 JSON 信封与策略

```json
{"$vt":"1","$type":"Point2","$data":{"x":1,"y":2}}
```

- `$vt/$type/$data` 是保留键；读侧可用 `detectExtensions=false` 关闭识别；
- `$vt` 是版本号：认得出信封但版本不是 `"1"` 时报 `VersionMismatch`（与二进制头一致），
  不能退化成普通 map 让类型信息无声丢失；
- 默认 `Auto`：用户扩展写信封、plain codec 写普通数据；`EnvelopeAll` 全部写信封；`Reject` 用于"纯数据"输出；`Flatten` 是有损降级；
- 未注册 codec 时**报错**（`UnknownType`），绝不静默把扩展变成 list/map。

数字策略：

- 整数写成整数（`int64` 全范围）；double 的整值补 `.0`，保证读回类型不变；
- 超过 `int64` 的整数读成 double；
- NaN/Inf 默认报错，可选写 `null`（`NonFinitePolicy::Null`）。

### 8.3 自写 JSON 的边界

解析器是严格子集：拒绝注释、尾随逗号、前导零、`+1`、`.5`、孤立代理对、
非法 UTF-8、根值后的多余字符。带字节偏移 + 行列错误。

防护：

- 最大嵌套深度（默认 256）；
- 数字用 `std::from_chars` / `std::to_chars`（locale 无关、最短往返）；
- 字符串必须是合法 UTF-8；
- 解析直接产出 Variant，不建中间 DOM。

### 8.4 二进制格式

```
'V' 'T' 'B' 0x01 + 递归标签
00 null / 01 false / 02 true
03 int64 + zigzag varint
04 double + 8 字节 IEEE754 小端
05 string + varint 长度 + UTF-8
06 list + varint 数量 + value*
07 map + varint 数量 + (key + value)*
08 extension + 类型名 + value
```

- 显式小端，不 `memcpy` 结构体；
- 扩展用**类型名**而不是数字 id，注册表顺序变化不影响旧数据；
- 读取先校验长度再分配；有 `maxStringBytes` / `maxElements` / 深度上限。

### 8.5 测试

`vt_serial_tests`（1700 项）：

- 内建类型边界（INT64_MIN/MAX、±0.0、1e-300、最大 double、Unicode、控制字符）；
- JSON 严格错误表（前导零、尾随逗号、孤立代理、非法 UTF-8、深度）；
- 二进制截断/坏 magic/版本/尾随数据/长度炸弹；
- codec：值类型、`std::vector<int>`、指针类型、Reject/Flatten/未知类型；
- 500 组随机 Variant 的 JSON/二进制交叉往返；
- 2000 组随机字节输入不崩溃。

诚实边界：这不是带覆盖率引导的 fuzz，也没有 ASan 跑过；如果以后接收不可信输入，
建议接入 fuzz 语料和 ASan 再加固。
