# 升级说明：容器自动递归与两个 Sink

> 适用：`feature/container-traits` 分支相对 `main` 的变化（2026-11-01）。
> 面向要部署本分支、或从旧版本升上来的接入方。设计背景见
> [设计说明 5.4.1](设计说明.md) 与 [值遍历改造计划](值遍历改造计划.md)。

## 1. 一句话

**C++ -> Python 的容器映射键现在保留真实类型；序列化输出不变。**
若你的 Python 代码依赖"非字符串键是字符串"，需要改；C++ 侧只用公开 API 的代码不用动。

## 2. 破坏性变更（升级必须处理）

| 变更 | 之前 | 现在 | 影响面 |
| --- | --- | --- | --- |
| C++ -> Python 映射键 | `map<int,int>` -> `{"1": 2}` | `{1: 2}` | Python 侧对键类型敏感的取值/断言/比较 |
| 对象/指针键 | 退化成 `[[k,v], ...]` 的 list | `{DemoNode: ...}` 的 dict | 新能力；依赖 list 形态的 Python 代码要改 |
| `vt::detail::NormalizerFn` | `Variant (*)(const std::any&)` | `void (*)(const std::any&, ValueSink&)` | 直接调 `registerNormalizer`/`findNormalizer` 的 C++ 代码（编译期报错，不会静默） |
| `vt::detail::normalizeToVariant` | 唯一的递归实现 | 变成 `visitValue + VariantSink` 的一行包装 | 返回值与行为不变；需要"边算边写"时可自己实现 Sink |

**不受影响的反向路径**：Python -> C++ 仍把 dict 的键字符串化进 `VariantMap`
（`VariantMap` 只有字符串键），`getAs<map<int,...>>` 负责解析回来。这是有意的
不对称：只有 "C++ 知道类型" 的那一侧能保留键类型。

## 3. 不变的部分（不用动）

- **JSON / 二进制输出逐字节不变**（`vt_serial_tests` 1821 项，含 500 个随机
  `Variant` 的双格式交叉与 2000 组随机字节）；
- 存储仍是紧凑扩展槽（`vector<int>` 100 万元素 ≈ 4 MB，不是逐元素 `Variant`）；
- `getAs<T>` / `denormalizeFromVariant` 行为不变；
- 注册入口 `vpy::registerPointerType / registerValueType / registerSharedType` 不变；
- 只读进程的编译期锚点 `vt::registerContainerAdapters<T>()` 不变。

## 4. 升级 checklist

1. **搜 Python 侧对字符串键的依赖**：`{"1": ...}`、`d["7"]`、`json` 风格的断言。
   如果只是把 dict 原样传回 C++，无需改动（反向仍字符串化）。
2. **搜 C++ 侧对 `normalizer` 符号的使用**：`findNormalizer` / `registerNormalizer`
   / `NormalizerFn`。用到了就按新签名改（见第 2 节）。
3. **只读进程补锚点**：只读 JSON/二进制、从不 `fromValue` 该容器类型的进程，
   必须 `vt::registerContainerAdapters<T>();`，否则 JSON 读回时找不到遍历函数。
4. **跑全量回归**（见第 7 节），确认水位一致。
5. **确认部署环境的 Python**：`variant_binding.pyd` 与 Python 次版本、shiboken6
   版本绑定，换环境必须重编（本机是 Python 3.9.9 + shiboken6）。

## 5. 已知限制

| 限制 | 表现 | 规避 |
| --- | --- | --- |
| 映射键是 `std::pair` / `std::vector` 等容器 | **Python 侧转 dict 时抛 TypeError**（键被构造成 list，不可哈希）；JSON 正常，写成 `[[k],v]` | 换可哈希键；或先转成字符串/元组再入 map |
| `vpy::canConvertToPython` 不能预测键可哈希性 | 预检返回 true，实际转换时才抛 TypeError | 预检只当"类型是否注册"的判断，不要当"一定成功"的闸门 |
| 不可哈希键的报错 | 是 Python 原生 `unhashable type: 'list'`，不带"哪个 map"的上下文 | 转换入口自己补日志 |
| `vt::detail::ValueSink` / `visitValue` | 内部扩展点，**不承诺 API 稳定性** | 需要自定义输出时，拷贝一份实现而不是依赖它 |
| 跨编译器 | 只在 MSVC 2019（Release / core Debug）验证过 | 换 GCC/Clang 前先跑一遍回归 |

## 6. 性能数据（本机 Release / MSVC 2019，`vt_bench` 的 value traversal 段）

| 场景 | 遍历 `visit(ms)` | 手写循环 `direct(ms)` | 比值（4 次运行） |
| --- | --- | --- | --- |
| `vector<int>` 20 万 | 2.97 ~ 3.10 | 2.28 | 1.30 ~ 1.36x |
| `vector<vector<int>>` 1000 x 100 | 2.82 ~ 2.87 | 2.18 ~ 2.27 | 1.24 ~ 1.32x |
| `map<string,int>` 2 万 | 2.73 ~ 2.78 | 2.53 ~ 2.61 | 1.05 ~ 1.08x |
| `map<int,int>` 2 万（键写文本） | 2.66 ~ 2.68 | 2.58 ~ 2.73 | 0.98 ~ 1.04x |

读法：

- `direct` = 改造前 `normalizeToVariant` 的写法（手写递归、无事件），作为基线；
- 叶子最密的平坦序列仍有 ~30% 开销（每元素一次事件；`VariantSink` 已模板化内联，
  剩下的主要是 sink 里的分支），映射容器基本持平；
- **Python 侧未纳入基准**：`PySink` 省掉了中间的 `VariantList`（100 万 int 少约
  40 MB 临时 Variant），但绝对值没有单独测量。要报 Python 转换性能必须另做测量，
  不要引用本表。

  `python39_d.lib`，`_DEBUG` 会启用 `Py_DEBUG`）；

## 8. 回滚

改动集中在 `feature/container-traits` 分支；回滚到 `main` 会让 Python 侧键退回
字符串（数据兼容：JSON/二进制从未依赖键类型，读写互通）。
